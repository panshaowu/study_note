## 1\. 简介

分词和分词算法起到的是文本到模型的输入的一个桥梁，一段文本只有经过分词得到Token后，才能更好的被模型理解和接受，所以Tokenizer是模型的基础组件之一。模型对Token（令牌）的理解经历了word/char到subword（子词）的过程，分词算法也在不断更新适应目前大模型的输入。

## 2\. Token

### 2.1 word粒度

最初的分词是词维度，对于英文语境，词语是天然存在的，对于中日韩等语言，缺少先天词边界，但是可以通过分析算法解决这一问题（之前流行很多算法，包括jieba等算法）。使用word粒度作为Token输入模型的优缺点如下，

```html
中文句子：我喜欢看电影和读书。
分词结果：我 | 喜欢 | 看 | 电影 | 和 | 读书。
英文句子：I enjoy watching movies and reading books.
分词结果：I | enjoy | watching | movies | and | reading | books.
```

**优点：**

-   **语义丰富：**词语能保留文本大部分的语义，提高模型精度；
-   **上下文理解**：以词为粒度进行分词有助于保留词语之间的关联性和上下文信息，从而在语义分析和理解时能够更好地捕捉句子的意图。

**缺点：**

-   **OOV（Out-of-Vocabulary）问题**：模型训练所在的语料库很难覆盖所有词语的，所以会导致未收录词（OOV）问题。
-   **长尾问题：**词语作为Token，会导致词表很大，而且会有很多长尾词语和稀有词语，导致训练成本增大，而且稀有词语训练和学习难度也很大；
-   **词语之间关系无法学习的问题：**因为以词语作为Token，会导致形态或者词缀相似或一致的词语没有什么联系。

### 2.2 char粒度

除了以词粒度作为分词间隔，还可以以字符粒度作为分词间隔，这样可大大降低词表的大小，因为英文就26个字母，中文常用的6000多个词，而且基本可以避免OOV问题，同时分词算法简单（不用考虑中文分词问题）。以char作为分词粒度的优缺点：

```text
中文句子：我喜欢看电影和读书。
分词结果：我 | 喜 | 欢 | 看 | 电 | 影 | 和 | 读 | 书 | 。

英文句子：I enjoy watching movies and reading books.
分词结果：I |   | e | n | j | o | y |   | w | a | t | c | h | i | n | g |   | m | o | v | i | e | s |   | a | n | d |   | r | e | a | d | i | n | g |   | b | o | o | k | s | .
```

**优点：**

-   **词表小**：可以提高学习效率：
-   **避免了OOV问题**。

**缺点：**

-   **语义信息不明确：**因为Token是char，长度很短却少，无法表达丰富的语义；
-   **序列长度大：**利用char粒度分词，序列长度会增大，增大计算量。

### 2.3 subword（子词）

上面发现基本上 word 分词的优点可以弥补 char 分词的缺点，而 char 分词的优点又恰好可以弥补 word 分词的缺点。因此，为了在**词表大小**、**计算效率**和**语义丰富度**之间取得最佳平衡，出现了 subword（子词）分词粒度。目前，subword 已经成为几乎所有主流大语言模型（如 GPT、LLaMA、BERT 等）的标准分词方案。

**subword 的核心思想：**
将高频的常见词汇保留为完整的词，而将低频的罕见词汇拆分为更小、更基础的子词片段（甚至拆分到字符级别）。例如，在英文中，"unhappiness" 是一个相对低频的词，可能不在词表中，但它可以被拆分为 "un"、"happi" 和 "ness" 这三个高频的子词。

**subword 相比 word 和 char 的显著优势：**

1. **大幅缓解 OOV 问题（Out-of-Vocabulary）：**
   当模型遇到未见过的生僻词或拼写错误的词时，subword 算法会退而求其次，将其拆分为词表中已有的子词。在最极端的情况下，它可以退化为字符级别（char）的分词，从而保证任何文本都能被顺利编码，几乎彻底消除了 OOV 问题。
2. **控制词表大小，提高训练效率：**
   由于子词具有极高的复用性（例如词根、前缀、后缀），可以通过一个中等大小的词表（通常在 3 万到 10 万之间）覆盖绝大多数的自然语言文本，极大地减少了模型 Embedding 层的参数量和内存开销。
3. **保留语义信息，增强泛化能力：**
   很多子词本身就蕴含丰富的语言学形态信息（如复数后缀 "-s"、进行时后缀 "-ing"、否定前缀 "un-" 等）。当模型学习到 "un-" 代表否定含义时，即使遇到一个全新的词，只要它被拆分出了 "un-"，模型也能大致推断出它的语义倾向。这使得模型对新词和未登录词具有更强的语义泛化能力。

总而言之，subword 粒度是 word 粒度和 char 粒度的一种“优雅妥协”，完美适配了现代深度学习模型的需求。下面我们将详细介绍几种主流的 subword 分词算法的原理和实现细节。

## 3 Tokenizer算法

### 3.1 BPE算法

BPE算法的核心思想从一个很小的词表开始，不断合并出现频率最高的连续子词，得到一个新的子词添加到词表中，不断扩大词表，具体步骤如下：

1.  初始化词表：根据输入的预料得到初始的词表，或者直接定义词表，例如英文中26个字母加上各种符号以及常见中文字符，这些作为初始词表。
2.  拆分预料&计算子词频率：利用初始词表拆分预料库，并计算量量连续子词的出现频率；
3.  合并子词：合并出现频率最高的连续子词，合并后作为一个新子词添加到词表；
4.  更新子词频率：对于新加入的子词，计算其连续子词的频率（即合并前左右子词的左右频率）；
5.  重复2-4步骤：直到达到词表设置上限或者合并次数，或者直到不再有有意义的合并（即，进一步合并不会显著提高词汇表的效益）。
6.  **使用训练好的 BPE 分词器（贪心前向匹配）**：推断阶段对新文本进行分词时，同样将词拆成单个字符，然后按照 `merges.txt` 中记录的合并优先级从高到低、贪心地依次执行合并，直到无法再合并为止。这是一个确定性的过程。

**优势**：可以有效地平衡词汇表大小和编码步数（编码句子所需的 Token 数量，与词表大小和粒度有关）。

**劣势**：基于贪婪和确定的符号替换，不能提供带概率的多个分词结果（这是相对于 ULM 而言的）；decode 的时候面临歧义问题。

### 3.2 BBPE算法（Byte-level BPE）

根据名称可以知道，这是一个基于字节粒度的BPE算法，为了了解BBPE算法，需要先了解一些基础知识：

**Byte(字节)**：字节是计算机中的最小存储和数据处理单元，一个字节等于8位，常用的ASCII码就是用一个字节表示的。

**ASCII 码：** 美国信息交换标准代码（American Standard Code for Information Interchange）是基于拉丁字母的一套电脑编码系统，包括 26 个英文字母大小写、阿拉伯数字、常用符号及控制字符，共 **128 个**字符（编码范围 0~127），用一个字节的低 7 位表示。后来各厂商将高位也加以利用，扩展出了 Extended ASCII（256 个字符），但这并非官方标准。

**Unicode编码：**Unicode 是一种字符集，旨在涵盖地球上几乎所有的书写系统和字符。它为每个字符分配了一个唯一的代码点（code point）用于标识字符。但是Unicode 并没有规定如何在计算机内存中存储和传输这些字符。

**UTF-8：** UTF-8（Unicode Transformation Format-8）是一种变长的字符编码方案，它将 Unicode 中的代码点转换为字节序列，UTF-8 的一个重要特点是向后兼容 ASCII。在 UTF-8 编码中，字符的表示长度可以是 1 到 4 个字节：ASCII 字符占 1 字节，大多数拉丁文、希腊文等占 2 字节，**绝大多数常用汉字（CJK 统一汉字）占 3 字节**，部分极生僻字（Unicode 辅助平面字符，如部分 Emoji）才会占用 4 字节。

**Byte-level BPE(BBPE)：**

通过上面的基础知识应该了解，我们可以将任意一个字符在细拆成字节，利用字节来表示文本序列，英文文本一般是和两者一致的（因为英文字母都可以用一个字节表示），但是对于中文等其他语种，一个字符可能要拆成多个字节。所以BBPE和BPE算法区别就在于处理最小词汇的粒度从字符变成了字节，其他流程一样。理论上来说，BBPE算法不存在OOV问题，这也是目前主流大模型都采用他的一个原因。具体流程如下：

**优势**：1）**天然消除 OOV**：任何文本都可以用 256 个基础字节来兜底表示，从根本上杜绝了未登录词问题；2）**跨语言共享能力强**：不同语言的文字在字节层面可以直接共享子词单元，对多语言模型尤为友好；3）**即使字符集不重叠**（如中文与阿拉伯文），也可以通过字节层面的共享实现语言间的良好迁移。

**劣势**：1）对于非 ASCII 文本（如中文），编码后的序列长度可能显著长于字符级 BPE，增加计算成本；2）从字节序列解码回文本时，需要正确处理多字节字符的边界，否则可能产生无效字节序列（`replacement character \uFFFD`）。

1.  初始词表：构建初始词表，包含一个字节的所有表示(256)。
2.  构建频率统计：统计所有子词单元对（两个连续的子词）在文本中的出现频率。
3.  合并频率最高的子词对：选择出现频率最高的子词对，将它们合并成一个新的子词单元，并更新词汇表。
4.  重复合并步骤：不断重复步骤 2 和步骤 3，直到达到预定的词汇表大小、合并次数，或者直到不再有有意义的合并（即，进一步合并不会显著提高词汇表的效益）。
5.  分词：使用最终得到的词汇表对文本进行分词。

### 3.3 Wordpiece算法

Google的Bert模型在分词的时候使用的是WordPiece算法。与BPE算法类似，WordPiece算法也是每次从词表中选出两个子词合并成新的子词。与BPE的最大区别在于，如何选择两个子词进行合并：BPE选择频数最高的相邻子词合并，而WordPiece选择能够提升语言模型概率最大的相邻子词加入词表。

注：这里所说的“语言模型”并不是如n-gram或者神经网络这样的模型，而是统计学模型。

看到这里，你可能不清楚WordPiece是如何选取子词的。这里，通过形式化方法，能够清楚地理解WordPiece在合并这一步是如何作出选择的。假设句子 $ S=(t_{1},t_{2},...,t_{n})$由n个子词组成，$t_{i}$表示子词，且假设各个子词之间是独立存在的，则句子$S$的语言模型似然值等价于所有子词概率的乘积：

$logP(S) = \sum_{i=1}^{n}logP(t_{i}) \\$

假设把相邻位置的x和y两个子词进行合并，合并后产生的子词记为z，此时句子$S$似然值的变化可表示为：

$logP(t_{z})-(logP(t_{x})+logP(t_{y}))=log(\frac {P(t_{z})}{P(t_{x})P(t_{y})}) \\$

从上面的公式，很容易发现，似然值的变化就是两个子词之间的**互信息（Mutual Information，MI）**。简而言之，WordPiece 每次选择合并的两个子词，他们具有最大的互信息值，也就是两子词在语言模型上具有较强的关联性，它们经常在语料中以相邻方式同时出现。

**WordPiece 的 `##` 前缀标记**：WordPiece 在训练和推断时，会对词中非词首位置的子词添加 `##` 前缀，以区分该子词是"词首片段"还是"词中/词尾片段"。例如 `playing` 会被切成 `play` 和 `##ing`，其中 `##ing` 明确表示它不是一个独立的词，而是紧跟在前一个子词后面的连续片段。这使得模型在解码时可以无歧义地还原出原始单词边界，也是 BERT 系模型词表中大量出现 `##` 开头词条的原因。

### **3.4 Unigram Language Model (ULM)**

与WordPiece一样，Unigram Language Model(ULM)同样使用语言模型来挑选子词。不同之处在于，BPE和WordPiece算法的词表大小都是从小到大变化，属于增量法。而Unigram Language Model则是减量法,即先初始化一个大词表，根据评估准则不断丢弃词表，直到满足限定条件。ULM算法考虑了句子的不同分词可能，因而能够输出带概率的多个子词分段。

1.  初始时，建立一个足够大的词表。一般，可用语料中的所有字符加上常见的子字符串初始化词表，也可以通过BPE算法初始化。
2.  针对当前词表，用EM算法求解每个子词在语料上的概率。
3.  对于每个子词，计算当该子词被从词表中移除时，总的loss降低了多少，记为该子词的loss。
4.  将子词按照loss大小进行排序，丢弃一定比例loss最小的子词(比如20%)，保留下来的子词生成新的词表。这里需要注意的是，单字符不能被丢弃，这是为了避免OOV情况。
5.  重复步骤2到4，直到词表大小减少到设定范围。

## 3.6 特殊 Token（Special Tokens）

特殊 Token 是 Tokenizer 体系中不可忽视的重要组成部分。它们不代表真实的自然语言词汇，而是起到**结构控制和信号传递**的作用。不同模型和任务使用的特殊 Token 略有差异，但核心类型如下：

| 特殊 Token | 常见写法 | 含义与用途 |
|---|---|---|
| 句子开始 | `<bos>`, `[CLS]`, `<s>` | 标记一段输入的开头，`[CLS]` 在 BERT 中还用于提取句子级分类特征 |
| 句子结束 | `<eos>`, `[SEP]`, `</s>` | 标记生成的结束，或分隔两个输入句子（BERT 双句任务） |
| 填充 | `[PAD]`, `<pad>` | 将同一 batch 中不等长的序列补齐到相同长度，填充位置会被 Attention Mask 遮盖 |
| 掩码 | `[MASK]` | 在 BERT 式掩码语言模型（MLM）训练中，遮盖需要模型预测的 Token |
| 未知词 | `[UNK]`, `<unk>` | 在 BBPE 之前的模型中，遇到词表外词汇时使用的占位符 |
| 角色控制 | `<\|system\|>`, `<\|user\|>`, `<\|assistant\|>` | 现代对话大模型（如 ChatML 格式）中用于区分不同角色的对话轮次 |

> [!NOTE]
> 特殊 Token 需要在词表中占据固定的 ID（通常是头部低 ID），并在训练和推断时保持绝对一致。特殊 Token 的 Embedding 向量是独立学习的，不受普通子词合并规则约束。

## 4 **SentencePiece**

如何使用上述子词算法？一种简便的方法是使用SentencePiece，它是谷歌推出的子词开源工具包，其中集成了BPE、ULM子词算法。除此之外，SentencePiece还能支持字符和词级别的分词。更进一步，为了能够处理多语言问题，SentencePiece将句子视为Unicode编码序列，从而子词算法不用依赖于语言的表示。

具体来说，SentencePiece的优点：

1.  不需要预处理：传统的BPE需要先将句子分词、特殊符号处理等预处理，SentencePiece可以直接处理原始文本，不需要预处理文本；
2.  子词处理功能更强大：传统BPE从字符开始不断合并成子词，SentencePiece算中的BPE不仅能处理单字符级别，还可以处理包含特殊字符的文本，能自动区别空格和标点符号；
3.  性能与适用性：传统BPE适合处理结构比较清晰的语言，对需要额外处理的语言可能显得笨重。SentencePiece更加灵活，适用于多种语言，尤其是复杂的、包含空格和标点的自然文本；在处理跨句子和特殊字符方面表现更好。
4.  词表生成：传统 BPE：依赖频率统计和合并生成词表，过程相对简单。SentencePiece：支持多种分词算法，提供了广泛的词表生成选项和优良的语言支持；
5.  处理速度：SentencePiece的处理速度比BPE更快。

## 5 词表构建实践：复用还是定制？

在实际工业落地中，每次启动大模型训练前是否需要重新定制词表，主要取决于你所处的**训练阶段**和**目标任务**。通常分为以下三种情况：

### 5.1 直接复用（微调阶段 SFT / RLHF）

如果你是在已有的开源大模型（如 LLaMA-3、Qwen、ChatGLM 等）基础上进行**微调（SFT / LoRA）**，你**必须且只能直接复用**该模型原有的词表和 Tokenizer。
* **原因**：大模型的 Embedding 层和输出层（lm_head）的权重矩阵大小是和词表大小严格绑定的。如果你修改了词表，原本学好的权重就会错位或失效，导致模型完全丧失原本的语言能力。

### 5.2 词表扩充（继续预训练 Continual Pre-training）

假设你拿到一个英文能力极强但中文很弱的开源模型，或者你需要让模型学习大量的垂直领域黑话（如医疗、法律、代码），你可以选择**“复用 + 扩充”**。
* **做法**：保留原开源模型词表的基础，利用你自己的领域语料再训练出一个补充词表（例如两万个中文字词），把两者合并。
* **代价**：新增的词汇在模型里是没有对应的权重的，因此你**必须进行一次代价较大的“继续预训练”**，让模型学到这些新词的语义表示，然后才能进入微调阶段。著名的 `Chinese-LLaMA` 采用的就是这种策略。

### 5.3 从头定制构建（从零预训练 Pre-training from scratch）

如果你准备从零开始训练一个全新的基础大模型，你才需要面临是否定制词表的选择：
* **直接复用（如复用 GPT-4 或 LLaMA 的词表）**：可以省去训练 Tokenizer 的麻烦。
* **定制构建（强烈建议）**：因为你的训练语料分布肯定和前人不同。针对你自己的海量预料（比如包含了大量的中文和代码）重新跑一遍 BPE 或 BBPE 算法，能够使得分词在你的语料上**“编码效率最高”**。编码效率高意味着原本需要 10 个 token 表达的一句话，现在可能只需要 6 个 token。这不仅能变相延长大模型的上下文窗口，还能极大地降低推理成本并提高训练速度。

## 6 Tokenizer 的工程落地：文件结构与运行时逻辑

在理解了各种 Tokenizer 算法后，很多开发者在实际应用中经常会混淆“词表”与“Tokenizer”的概念，并对它们在底层是如何调用和运作的产生疑问。

### 6.1 概念区分：数据 vs 算法

*   **词表（Vocabulary）**：本质上是一个“映射字典”数据结构。它只负责静态存储，比如存储着所有 Token 以及它们对应的 ID（例如：`{"我": 10, "apple": 809}`）。
*   **Tokenizer（分词器）**：执行分词动作的“代码逻辑/算法”。它负责决定用哪种规则（如 BPE、WordPiece）把输入的原始句子切开，切开后再去**查词表**，将子词转换为 ID 序列喂给大模型。

简而言之：**词表是数据，Tokenizer 是查字典的方法与执行程序。**

### 6.2 物理文件结构

在开源社区（如 HuggingFace 下载的模型）中，模型的分词组件并非千篇一律的单个文件，主要分为两派：

1.  **散装文件派（数据与规则分离）**：以早期的 GPT-2、RoBERTa 为代表。
    *   `vocab.json`：纯粹的词表文件，存储 Token 到 ID 的映射。
    *   `merges.txt`：BPE 等算法特有的合并规则表。Tokenizer 依赖此表来决定相邻字符的合并优先级。
    *   `tokenizer_config.json`：存放 Tokenizer 的各类配置参数（如谁是未知词 `[UNK]`，谁是结束符 `[EOS]`）。
2.  **打包文件派（数据与规则高内聚）**：以 LLaMA、ChatGLM 等现代模型为代表，为了提高加载速度和一致性进行了打包。
    *   **SentencePiece 模型 (`.model` 文件)**：二进制文件，**内部同时包含了词表静态映射以及 ULM/BPE 的切词概率和动态规则**。
    *   **HuggingFace Fast Tokenizer (`tokenizer.json` 文件)**：基于 Rust 编写的高效分词引擎，将原本散装的 `vocab.json` 和 `merges.txt` 等信息整合进了一个统一的大 JSON 文件中。

### 6.3 运行时调用逻辑（内存加载 vs 磁盘 I/O）

在实际的大模型推理或训练过程中，`vocab.json` 和 `merges.txt` 这类文件**绝对不会被实时、反复地从磁盘读取**，否则极慢的磁盘 I/O 会直接卡死整个模型的吞吐。其实际工作机制如下：

1.  **仅在初始化阶段加载（Load into Memory）**：
    当代码实例化 Tokenizer 时（例如执行 `AutoTokenizer.from_pretrained(...)`），程序仅会去硬盘进行一次 I/O 操作，将相关文件完整读取并加载到计算机内存（RAM）中。
    *   `vocab.json` 会被转换成内存里的**哈希表（Hash Map / 字典）**，以实现 $O(1)$ 的极速 ID 查找。
    *   `merges.txt` 会被解析成**优先级队列**或**前缀树（Trie Tree）**等高效数据结构，用于快速检索字符串合并规则。
2.  **纯内存中的实时分词执行流水线（In-Memory Processing Pipeline）**：
    一旦初始化完成，硬盘上的文件便不再被访问。当有一句真实的文本输入（如 `"I like apples!"`）时，Tokenizer 会在内存中严格按照以下四个步骤执行流水线操作：
    *   **Step 2.1 预处理与初步切分（Normalization & Pre-tokenization）**：首先对文本进行清洗（如统一小写、清理非法字符等），然后按照空格和标点符号将长句子粗略切分成基础词块（如 `["I", "like", "apples", "!"]`）。
    *   **Step 2.2 核心子词合并（Subword Tokenization）**：针对每一个基础词块，Tokenizer 开始查询内存中的 `merges` 数据结构（前缀树/优先级队列）。以 BPE 为例，它会将 `apples` 拆成单个字符 `a, p, p, l, e, s`，然后根据内存中记录的合并优先级，一步步将其合并为 `app` 和 `les`，直到没有更高优先级的合并规则为止。
    *   **Step 2.3 查表映射（ID Mapping）**：合并结束后，Tokenizer 会拿着最终得到的子词序列（如 `["I", "like", "app", "##les", "!"]`），去内存的 `vocab` 哈希表中进行 $O(1)$ 时间复杂度的查表，将字符串瞬间转换为对应的整数 ID 序列（如 `[1045, 2066, 10448, 4398, 999]`）。
    *   **Step 2.4 后处理（Post-processing）**：最后，根据模型特定的配置，在 ID 序列的开头或结尾拼接特殊的控制符，如 `[CLS]` (句首)、`[SEP]` (句尾) 或 `<bos>`、`<eos>`，最终生成喂给大模型 Embedding 层的输入。

这套纯内存的流水线设计，加上 Rust、C++ 等底层编译语言的加持，使得现代 Tokenizer（如 HuggingFace Fast Tokenizer）能够轻松实现每秒处理数十万甚至数百万 Token 的极高吞吐量。

## 7 分词结果的确定性与随机性（BPE Dropout 与 ULM 采样）

关于“对于同一段文字，分词结果是否固定”，需要区分不同的算法机制和工程运行阶段：

### 7.1 分词算法的理论确定性

*   **BPE / BBPE / WordPiece**：属于**确定性算法**。在推断阶段，它们依赖确定的规则表（如 `merges.txt`），采用贪心前向匹配进行切分。对于相同输入文本，输出的分词结果是唯一且固定的。
*   **ULM (Unigram Language Model)**：属于**概率语言模型**。理论上，同一段文字可能存在多种合法的子词切分组合，ULM 能计算出每种路径的概率。但在标准推理阶段，为了保证输出稳定，默认会使用维特比算法（Viterbi）选取概率最高的最优路径，因此**结果也是固定的**。

### 7.2 训练阶段的数据增强：分词正则化

为了防止模型对特定分词形式产生过拟合、增强模型对拼写错误或新词的泛化能力（尤其是早期的神经机器翻译 NMT 场景），工业界引入了**分词正则化（Subword Regularization）**：

*   **BPE Dropout**：在 BPE 合并过程中，以一定概率（如 0.1）随机跳过某些合并规则。使得同一单词在不同训练轮次被切分为不同的 Token 序列（如 `preprocessing` 随机切为 `["pre", "processing"]` 或 `["pre", "pro", "cessing"]`）。
*   **Unigram 采样（Unigram Sampling）**：在 ULM 框架下，按前向-后向算法计算出的概率分布，随机采样产生不同的分词组合。

**注意：** 当开启 BPE Dropout 或 ULM 采样时，**分词结果是动态随机、非固定的**。但这仅限于训练阶段，推理时必须关闭以保证确定性。

### 7.3 近年 SOTA 大语言模型的实际工程选择

对于近几年发布的顶尖前沿大模型（如 LLaMA 3, DeepSeek-V3/V4, GLM-5.2, Kimi K3 等），在预训练和强化学习（RLHF）阶段，**默认绝对不开启 BPE Dropout**，而是全部坚持采用确定性的离线静态分词（Offline Deterministic Tokenization）。原因在于：

1.  **致命的工程计算瓶颈：** 极大规模模型预训练数据（数十万亿 Token）必须完全离线二进制化（Offline Packing）。如果开启 BPE Dropout，则需要在 CPU 侧执行“实时动态切词（On-the-fly Tokenization）”，这将彻底卡死 DataLoader，导致万卡 GPU 集群空转。
2.  **极长上下文与前缀缓存（Prefix Caching）失效：** Kimi K3（1M 上下文）等模型极度依赖 KV Cache 的前缀复用和上下文并行（KCP）。若分词存在随机性，每次切出的 Token 序列不同，前缀缓存将彻底失效。
3.  **单 Epoch 范式无需防过拟合：** 现代大模型预训练数据极具多样性，模型对海量数据基本只过一遍（Single-pass），几乎不存在早期机器翻译模型中固定切分导致的过拟合风险。
4.  **排除强化学习的训推不一致：** 在 RLHF 阶段，四个模型（Actor, Critic, Reward, Reference）必须严密对齐。采用绝对确定性的分词，可以从根本上杜绝“因分词随机性导致训推分布偏移”的隐患。目前的“训推不一致”痛点更多集中在 Chat Template 拼接、思维链长度截断与暴露偏差上，而非算法切词的随机性。
